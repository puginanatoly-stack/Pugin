# Ситуация (контекст)

После сборки самого weather-dashboard (4 вкладки, 8 источников данных, интегральный индекс) Анатолий попросил закоммитить всё в GitHub, чтобы раз в день по расписанию запускалось и слало в Telegram уведомление, если «не спокойно». На вопрос про репозиторий сказал: «я думаю публичный сделать... там ведь нет критичного ничего и секретов нет». Дальше — реализация: создание репо, приватно-публичный сплит данных, упор в ограничение прав токена, ручные секреты, и в конце — киберпанк-стилизация Telegram-сообщения с переключателем режима через секрет.

# Мои мысли (chain of thought)

На «там нет ничего критичного» не согласился молча и не переспорил в лоб — проверил по существу: `data/history.jsonl`, который сам же только что спроектировал, накапливает точный город и время каждого запуска. А в собственном PRINCIPAL_IDENTITY.md принципала поле Location уже осознанно оставлено пустым — то есть решение «не палить геолокацию» уже было принято им один раз, публичный репо с растущей историей погоды конкретного города тихо бы его отменил. Это не абстрактный принцип «приватность важна», а конкретное противоречие с уже сделанным его собственным выбором — поэтому стоило прямо назвать, а не поставить дисклеймер и продолжить.

Решение — не «сделать репо приватным» (это его прямо предложенный вариант, но убивает саму идею публичного кода) и не «просто предупредить и оставить как просил» — а структурный сплит: код в публичном репо, накапливающаяся история — в уже существующем приватном ai_agent, куда у токена и так есть доступ. Приватность стала свойством архитектуры (данные физически не долетают до публичного гит-лога), а не полем внимательности человека, которое рано или поздно ослабнет.

Дальше — вместо изобретения нового способа «раз в день + Telegram», вспомнил, что в OPERATIONAL_RULES уже задокументирован ровно этот паттерн (GitHub Actions cron + curl + repo secrets) для семейной рассылки, и там же прямо записан провал предыдущей попытки — Claude Code cloud routines не могут трогать Telegram-токен, флагуются как exfiltration. Не стал заново нащупывать это же грабли — взял уже проверенный путь целиком.

По пути каждый внешний источник (NOAA rtsw, EONET, USGS, Yahoo Finance, RSS-ленты) проверялся curl'ом до того, как под него писался код — поймал этим два реальных краевых случая (MOEX отдаёт пустой quote.close, Yahoo банит без браузерного User-Agent), а не после того, как код бы тихо упал в проде. Тот же принцип на последнем шаге: не поверил зелёному git push — реально задиспатчил workflow через API и дождался статуса completed, прежде чем сказать «готово».

Когда уткнулся в то, что fine-grained PAT не может писать в свежесозданный им же самим репозиторий (создание — account-level право, запись — per-repo allowlist), и Анатолий попросил «добавь сам» — не стал изображать попытку или тихо обходить это чем-то более широким токеном, а прямо объяснил, что у GitHub нет API для расширения repository access уже выпущенного fine-grained токена — структурное ограничение, не вопрос усилия.

Под конец, когда попросил «переключатель заложить в секреты» — реализовал NOTIFY_MODE именно как секрет GitHub Actions, потребляемый workflow'ом, а не как константу в коде, хотя константа была бы на одну правку проще. Место контрола — там, где явно попросили, не там, где было бы минимально удобнее реализовать.

# Принципы и паттерны

- **Privacy through architecture, not disclaimer.** Когда всплыл конфликт с уже принятым решением принципала (Location: skipped) — решение не в предупреждении и не в молчаливом согласии, а в структурном разделении публичного/приватного так, чтобы утечка стала физически невозможна, а не просто менее вероятна.
- **Reuse proven infra over reinventing.** Прежде чем проектировать «раз в день + Telegram» с нуля — вспомнил и применил уже задокументированный, уже работающий паттерн (и уже известный провал альтернативы), не наступил на ту же грабли второй раз.
- **Verify every seam for real, not just the happy path in your head.** curl каждого внешнего API до кода; реальный workflow_dispatch + polling до completed вместо доверия зелёному git push.
- **Honest boundary on tool capability.** На прямую просьбу сделать то, что структурно невозможно через доступные инструменты — объяснил почему, а не изобразил попытку или тихо обошёл через более широкие права.
- **Control surface where explicitly asked, not where easiest.** Переключатель режима — в GitHub secret, как попросили, не в коде, хотя код был бы проще.

# Принятое решение и действие

Создан публичный `puginanatoly-stack/weather-monitor` — только код + workflow. История (`history.jsonl`) синхронизируется с приватным `ai_agent` через `history_sync.py` (pull/push через Contents API). `notify.py` — киберпанк-стилизованный Telegram-статус с переключателем `NOTIFY_MODE` (always/condition) через секрет. Полный пайплайн протестирован дважды вживую через `workflow_dispatch`, оба раза `conclusion: success`, реальное сообщение дошло в семейный чат.

# Итог и ретроспектива

Самая дешёвая проверка (перечитать собственный PRINCIPAL_IDENTITY.md на предмет «уже решённого один раз») спасла от того, чтобы тихо отменить осознанный выбор принципала под видом выполнения его же прямой просьбы «делай публичный». Сделал бы так же снова: когда прямая инструкция противоречит уже зафиксированному где-то ещё решению того же человека — называть это прямо, до реализации, не после.
